# Ozon Ops Agent — архитектура автономного агента управления магазином

## 0. Чем мы НЕ дев-пайплайн: строим дом для агента, не конвейер кода

У дев-агента (Cursor, Claude Code) продукт — **код, который остаётся** в репо; сессии одноразовые, артефакт — PR. У нас продукт — **решения и действия во внешнем мире** (цена изменена, отзыв отвечен, из акции вышли), а мир живёт на серверах Ozon, не в нашем git. Отсюда инверсии:

| | Дев-агент | Наш ops-агент |
|---|---|---|
| Продукт | код в репо | действия в ЛК + отчёты команде |
| Истина | git (код = истина) | ЛК Ozon; в репо — лишь наша модель мира |
| Задачи | уникальные, → PR | **повторяющиеся ежедневно** + сиюминутные «в моменте» |
| Что улучшается со временем | кодовая база | **плейбуки** (как делать задачу) и модель мира |
| Верификация | тесты/CI | обратное чтение API + метрики магазина |
| Время | нет часов | **дедлайны в часах** (отгрузка до 19:00), календарь, пики продаж |
| Скрипты | первичны | **вторичны** — руки для денежных операций, не продукт |
| Git-цикл | worktree→PR→CI→merge | main-only, агент коммитит журнал/состояние напрямую |

**Метафора дома:** CLAUDE.md — правила дома · `state/` — прихожая («что сейчас происходит») · `memory/` — библиотека (долгие факты) · `journal/` — дневник (прошлое) · `playbooks/` — кулинарная книга (как делаются повторяющиеся дела) · `tools/` — мастерская · календарь — ежедневник. Сессии приходят и уходят — дом остаётся.

Три следствия, которых нет в дев-мире:

1. **`state/` — первоклассный объект.** У дев-агента роль «что сейчас» играют `git status` и список PR. У нас нужен явный слой: открытые заказы с дедлайнами, ожидающие апрувы, активные акции и эксперименты, незакрытые треды, «что я жду от команды». Каждая сессия **начинается с чтения state** и **заканчивается его обновлением** — это и есть механика передачи дел между эфемерными сессиями (вместо PR-цикла).
2. **Плейбуки — это и есть «кодовая база».** Повторяющаяся задача (ответы на отзывы, репрайс, дайджест) описана плейбуком: шаги + guardrails + чек верификации. Ретро правит плейбук, а не код. Скрипты появляются позже, когда шаг плейбука стабилизировался и его дешевле детерминировать («сначала процедура, потом автоматизация» — не наоборот).
3. **Часы и календарь.** Дедлайн отгрузки, окно акции, 25-е число (налоги), пиковые распродажи — агент живёт в календаре. Роутины — не просто cron, а ежедневник с напоминаниями, который агент сам пополняет («напомнить 26.06 про КУДиР»).

Из дев-паттернов сознательно оставляем только то, что переносится: конституция, память, ретро-цикл, постмортемы, журнал, drift-check, верификация действий, tier-автономия. PR/CI/worktree — не тащим.

Агентная механика в духе [Cursor agent best practices](https://cursor.com/blog/agent-best-practices), перенесённая с разработки на менеджмент маркетплейса. Cursor-паттерн → наш аналог:

| Cursor (разработка) | Мы (маркетплейс) |
|---|---|
| Rules в `.cursor/rules/` | Конституция `CLAUDE.md` + гайдлайны по доменам |
| Тесты как verification target | Каждое действие проверяется обратным чтением API |
| Git worktree изоляция | Изоляция по доменам: pricing / reviews / cards / finance |
| Fresh conversation per feature | Каждая задача = свежая headless-сессия + память на диске |
| Rules update при повторной ошибке | Ретро → правка гайдлайнов + запись в память |
| Bugbot / review pass | TG-approve для необратимых действий + журнал всех действий |

## 1. Слои системы

```
┌─────────────────────────────────────────────────────────┐
│  ИНТЕРФЕЙСЫ                                              │
│  Telegram-бот (чат команды) · Google Sheets · CLI        │
├─────────────────────────────────────────────────────────┤
│  ОРКЕСТРАТОР (на сервере)                                │
│  Планировщик (cron) · Очередь задач · TG-мост ·          │
│  Ozon push-webhooks · Approval-механика                  │
├─────────────────────────────────────────────────────────┤
│  АГЕНТ (Claude Agent SDK, headless-сессии)               │
│  CLAUDE.md (конституция) · Skills · Memory · Subagents   │
├─────────────────────────────────────────────────────────┤
│  ДЕТЕРМИНИРОВАННЫЕ ТУЛЗЫ (Python/Node, не LLM)           │
│  ozon_api.py · sheets.py · pricing_engine.py · ledger.py │
├─────────────────────────────────────────────────────────┤
│  ДАННЫЕ                                                  │
│  SQLite (ledger, история цен, журнал действий) ·         │
│  memory/ (факты) · Google Sheets (командная витрина)     │
└─────────────────────────────────────────────────────────┘
```

**Ключевой принцип (из Cursor): всё, что касается денег — детерминированный код, LLM только решает.**
Агент не «прикидывает» цену в голове — он вызывает `pricing_engine.py`, который считает netback по формуле из `ozon-pnl-model.md`. Агент решает *что делать*, скрипт гарантирует *как посчитано*.

## 2. Уровни автономии (главная развилка дизайна)

| Tier | Что можно | Примеры | Механика |
|---|---|---|---|
| **T0 — читать** | всё, всегда | аналитика, новости, мониторинг цен конкурентов, исследования | полная автономия, результат в TG/Sheets |
| **T1 — обратимые действия** | автономно + лог | ответы на отзывы, правки описаний карточек, черновики | делает сам, постит в TG журнал «сделал X» |
| **T2 — деньги в guardrails** | автономно в коридоре | изменение цены в пределах floor/ceiling, выход из акции с отрицательной маржой | guardrails в конфиге: `цена ≥ netback_floor` (мин. маржа), `Δ за раз ≤ N%`; действие + отчёт в TG |
| **T3 — необратимое / крупное** | только с апрува | массовое изменение цен, отмена заказа, вывод стока, изменение стратегии | TG-сообщение с кнопками ✅/❌, таймаут = отказ |

Guardrails для T2 — файл `config/guardrails.yaml`:
```yaml
pricing:
  min_margin_pct: 3        # чистая маржа после всего не ниже
  max_change_per_step: 5   # % изменения цены за одно действие
  max_changes_per_day: 2   # на SKU
  floor_source: netback    # цена ≥ себестоимость / (netback_rate - min_margin)
promos:
  auto_exit_if_margin_below: 0
reviews:
  auto_reply_rating_gte: 4  # 1-3 звезды — драфт на апрув
```

## 3. Сервер и рантайм

**Минимальный стек** (можно поднять за вечер):
- **VPS / мини-ПК** (или твой Mac + tailscale), Linux, Node 20+ + Python 3.12.
- **Claude Agent SDK** (или headless `claude -p`) — каждая задача запускается свежей сессией с CLAUDE.md проекта (паттерн Cursor «fresh conversation per task»).
- **Оркестратор** — один процесс (Node или Python):
  - cron-расписание (routines ниже);
  - слушает Telegram (long polling — не нужен публичный IP);
  - принимает **Ozon push-уведомления** (новый заказ, отмена, статус — API `push notifications`) — если есть публичный endpoint; иначе поллинг раз в 5 мин;
  - очередь задач в SQLite: `id, type, payload, status, tier, result, approved_by`.
- **Секреты** — `.env` на сервере (Ozon ключи, TG-токен, Google service account).

**Почему очередь, а не «один вечный агент»:** контекст загрязняется (Cursor: «long conversations lose focus»). Каждая задача — изолированный запуск с нужными скиллами; общая память — на диске.

### 3a. Два слоя крона: датчики (без LLM) и агент (claude -p)

Не всё дергает `claude -p`. Дешёвые повторяющиеся проверки — чистый Python по крону, **датчики дома**:

```
watchers/ (cron, без LLM, каждые 5–15 мин)
├── orders_watcher.py    # новые заказы/отмены → snapshot в SQLite → алерт в TG напрямую
├── price_watcher.py     # наши цены + конкуренты → snapshot → триггер при выходе из коридора
├── reviews_watcher.py   # новые отзывы/вопросы → очередь
├── stock_watcher.py     # остатки < N дней продаж → триггер
└── drift_watcher.py     # ЛК == source of truth
```

Правило разделения: **датчик замечает и будит, агент думает и действует.**
- Событие не требует суждения («новый заказ, дедлайн 19:00») → датчик шлёт алерт в TG сам, LLM не нужен.
- Требует суждения (цена вне коридора → репрайс по плейбуку; отзыв 1★ → ответ) → датчик кладёт задачу в очередь → оркестратор запускает `claude -p` с плейбуком.

Это экономит токены, а датчики не галлюцинируют. `claude -p` на сервере гоняется для: задач из очереди, роутин с суждением (дайджест, ретро, аудит акций), вопросов из TG. Побочный бонус: датчики пишут снапшоты в SQLite всегда — история мира копится независимо от агента.

## 4. Структура репозитория (расширение текущего marketplaces/)

Система доков — по образцу внутреннего дев-проекта: **стабильные доки без дат и статусов (не гниют) + датированный journal (честно описывает прошлое, уборки не требует) + постмортемы как память об инцидентах**.

```
marketplaces/
├── CLAUDE.md                    # конституция агента (роль, автономия, правила) — читается каждой сессией
├── AGENTS.md                    # тот же контент для других агентов (Codex и т.п.)
├── HUMAN.md                     # гайд для КОМАНДЫ: как ставить задачи агенту, анти-паттерны, границы доверия
├── AGENT-ARCHITECTURE.md        # этот файл
├── config/
│   ├── guardrails.yaml          # границы T2
│   ├── routines.yaml            # cron-задачи
│   └── team.yaml                # кто в команде, роли, TG id, кто может апрувить
├── orchestrator/
│   ├── main.py                  # цикл: cron + TG + очередь
│   ├── tg_bridge.py             # бот: команды, апрувы, дайджесты (или takopi — см. §6)
│   └── queue.py
├── tools/                       # детерминированные тулзы (НЕ LLM)
│   ├── ozon_api.py              # обёртка всех вызовов (заказы, цены, отзывы, акции...)
│   ├── pricing_engine.py        # netback/маржа по ozon-pnl-model.md
│   ├── sheets.py                # Google Sheets read/write
│   ├── ledger.py                # финучёт в SQLite (+КУДиР-совместимо)
│   └── drift_check.py           # сверка: наш source of truth == фактическое состояние ЛК
├── state/                       # «ПРИХОЖАЯ» — что происходит сейчас (сессия читает первым, обновляет последним)
│   ├── NOW.md                   # открытые заказы+дедлайны, ждущие апрувы, активные акции/эксперименты, незакрытое
│   └── calendar.md              # ежедневник: налоговые даты, окна акций, напоминания (агент пополняет сам)
├── playbooks/                   # «КУЛИНАРНАЯ КНИГА» — повторяющиеся задачи: шаги + guardrails + чек верификации
│   ├── morning-digest.md
│   ├── repricing.md
│   ├── reviews.md
│   ├── promo-audit.md
│   ├── new-order.md             # вкл. дедлайн отгрузки и эскалацию
│   └── finance-weekly.md
├── docs/
│   ├── RUNBOOK.md               # операционка: сервисы, health, «что-то сломалось» (стабильный)
│   ├── BACKLOG.md               # очередь задач; правило: взял → сделал → вычеркнул в том же изменении
│   ├── PRODUCT.md               # магазин: ассортимент, поставщики, деньги, команда, ритм (стабильный)
│   ├── journal/                 # YYYY-MM-DD-<slug>.md — одна задача/сессия = один файл, append-only
│   └── incidents/               # постмортемы: симптом → root cause → как чинили → что поменяли → уроки
├── .claude/
│   ├── skills/
│   │   ├── ozon-seller-api/     # уже есть (swagger + lookup)
│   │   ├── wildberries-api/     # уже есть
│   │   ├── marketplaces-tax-ru/ # уже есть (КУДиР, УСН)
│   │   ├── pricing/             # правила ценообразования + формулы
│   │   ├── reviews/             # тон, шаблоны, эскалация
│   │   ├── cards/               # правила редактирования карточек
│   │   └── market-research/     # методика исследования конкурентов
│   └── agents/                  # субагенты: researcher, analyst, copywriter
├── memory/                      # факты (уже есть механика MEMORY.md)
├── data/
│   ├── store.sqlite             # цены, заказы, история, очередь
│   └── snapshots/               # дневные срезы (цены конкурентов, комиссии)
└── ozon-baza-znaniy/            # уже есть (офлайн-документация)
```

**«Куда смотреть» — таблица в CLAUDE.md** (паттерн дев-проекта): любая задача → сначала профильный док, не начинать с действий. Инцидент → RUNBOOK + похожие постмортемы. Контекст прошлых работ → journal.

## 5. Регулярные задачи (routines.yaml)

| Когда | Задача | Tier | Выход |
|---|---|---|---|
| каждые 15 мин | Заказы/отмены/споры (поллинг или push) | T0 | алерт в TG при новом заказе + дедлайне отгрузки |
| каждые 4 ч | Мониторинг цен: наши vs конкуренты (API + parsing) | T0→T2 | если наша цена вне коридора — корректировка в guardrails |
| ежедневно 08:00 | **Утренний дайджест**: продажи вчера, маржа, остатки, отзывы, индекс цен, алерты | T0 | пост в TG + обновление Sheets |
| ежедневно 09:00 | Новые отзывы/вопросы → ответы (4-5★ авто, 1-3★ драфт) | T1/T3 | ответы + драфты на апрув |
| ежедневно | Акции: аудит участия, маржа по каждой | T2 | автовыход при марже < 0, отчёт |
| ежедневно | Финучёт: транзакции Ozon → ledger → Sheets | T0 | свежая юнитка по SKU |
| пн 10:00 | Недельный отчёт: P&L, тренды, ДРР, возвраты | T0 | Sheets + TG-саммари |
| пн | Ресерч рынка/конкурентов (субагенты веером) | T0 | отчёт в Sheets |
| ежедневно | Новости платформы (digest в базе знаний Ozon + новости в ЛК API) | T0 | важное — в TG |
| 25 число | Налоговый чек: доход накопительно, приближение к порогам (НДС 20 млн!) | T0 | предупреждение заранее |
| еженедельно | **Ретро**: разбор журнала — где ошибся, что чинить в гайдлайнах | T0 | PR в CLAUDE.md/skills (паттерн Cursor) |

Проактивные предупреждения (то самое «если проебываемся») — это правило в каждой задаче: *любая аномалия против baseline* (маржа упала, невыкуп вырос, конкурент демпингует, дедлайн отгрузки < 3ч, сток < N дней продаж) → немедленный пинг в TG с severity.

## 6. Telegram: агент как сотрудник (архитектура)

**Ключевое техническое ограничение, из которого всё следует: один бот-токен = один polling-процесс.** Значит, токеном владеет ровно один процесс — **tg-bridge**. Всё остальное (датчики, cron-агенты, сессии) общается с телегой через него, по локальному HTTP.

```
                     Telegram (один бот, одна «личность»)
                                   │ polling
                        ┌──────────▼──────────┐
                        │      tg-bridge       │  владеет токеном
                        │  (aiogram, systemd)  │  логирует ВСЕ сообщения в SQLite
                        └──┬────────┬────────┬─┘
              локальный HTTP API (localhost):
              POST /send {chat,text,buttons}   ← датчики, cron-агенты, сессии
              POST /ask  {question,options,timeout} → блокирующий вопрос, вернёт ответ
              GET  /history {chat,limit}       ← агент читает контекст чата
                 │                 │                │
        ┌────────▼──────┐ ┌───────▼───────┐ ┌──────▼─────────┐
        │ DM-сессии      │ │ Тэг в чате    │ │ Кнопки/ответы  │
        │ (takopi-режим: │ │ → задача в    │ │ → резолвят     │
        │ reply = тред)  │ │ очередь       │ │ pending ask    │
        └────────────────┘ └───────────────┘ └────────────────┘
```

### Три режима — как у живого сотрудника

| Режим | Как выглядит | Verbosity |
|---|---|---|
| **Личка (DM)** | как takopi: пишешь — живая сессия, reply продолжает тред, resume-строка для терминала | полная, это парная работа |
| **Тэг в чате** | `@bot я купил 3 шт X по 30 000 — запиши в траты` → bridge заводит задачу → агент работает **молча** → в тред **один ответ с результатом** («Записал в ledger: 90 000 ₽, себестоимость X обновлена, маржа теперь 8,1%») | только результат; если задача долгая — одно «принял, делаю» и потом итог. **Никакого стрима шагов в чат** |
| **Проактив** | дайджесты, алерты датчиков, апрув-карточки с кнопками ✅/❌ (таймаут = отказ), вопросы агента команде | коротко, по делу |

### Скилл `tg` внутри сессий
Тонкий CLI поверх bridge API — любая сессия (серверная и локальная через ssh-туннель) может:
- `tg send` — написать в чат/топик;
- `tg ask "Выхожу из акции X, маржа −2,1%. Ок?" --options да,нет --timeout 4h` — спросить и дождаться;
- `tg history --limit 50` — прочитать, что обсуждала команда (bridge пишет всё в SQLite — агент «в курсе того, что происходит» без своего polling).

### Правила поведения (в CLAUDE.md)
- В чате говорит результатами, не процессом. Детали — по запросу или ссылкой на journal.
- Вопрос требует данных → сначала молча достаёт (ledger/API/история чата), потом отвечает одним сообщением.
- Упомянули деньги/факт мимоходом (не тэгнув) — **не вмешивается**, но может записать в память/ledger и тихо отметить в дневном дайджесте «зафиксировал: …» (не спамить).
- T3-апрувы — всегда карточкой с кнопками, не текстом «можно?».

### Путь внедрения
1. **День 1:** takopi как есть — личка работает.
2. **Неделя 1:** свой bridge (aiogram + `/send`, `/ask`, `/history`) — проактив, кнопки, тэги в чате. takopi остаётся для DM или его роль забирает bridge (DM-режим = тот же `claude -p --resume`, паттерн takopi).
3. Итог — **одна личность бота** во всех режимах.

**Локальная работа + один GitHub:** репо одно; сервер после каждой сессии коммитит и пушит `state/`+`journal/` (авто), локально — `git pull` перед работой (правило в CLAUDE.md). Конфликтов почти нет: NOW.md пишет в основном сервер, локально ты обычно работаешь над кодом/доками. Фолбэк без TG: ssh → `tmux new -A -s ops` → `claude`.

## 7. Google Sheets (командная витрина)

Sheets — не база, а **интерфейс для людей** (source of truth — SQLite + API Ozon):
- «Юнитка» — авто-обновление (как Ozon-юнитка-дроны.xlsx, но живое): цены, netback, маржа, себестоимость (команда вписывает — агент читает).
- «Финучёт» — транзакции, выплаты, P&L помесячно.
- «Цены» — текущие/floor/ceiling; команда может править floor — агент подхватывает как guardrail.
- «Задачи агенту» — строка со статусом = задача в очередь (для тех, кому TG неудобен).

## 8. Память и знания

Трёхуровневая (как сейчас, but formalized):
1. **CLAUDE.md** — конституция: роль, автономия, стиль общения, что никогда не делать.
2. **memory/** — факты с типами (user/project/feedback/reference), MEMORY.md индекс. Каждая ошибка после ретро → memory типа feedback («не менять ставку без сверки с API — кейс 42/43»).
3. **journal/** — append-only: каждое действие с timestamp, tier, результатом верификации. Это и аудит, и материал для ретро.

## 8a. Жизненный цикл сессии (вместо PR-цикла)

Каждая сессия (cron-роутина или вопрос из TG) проходит один контур:

```
старт → прочитал state/NOW.md + календарь + профильный плейбук
      → сделал (tier-правила, dry-run, верификация)
      → обновил NOW.md (что закрыл, что появилось, что жду)
      → [значимое?] запись в journal  → [ошибка мира?] постмортем
      → отчитался в TG (если есть что)
```

NOW.md — маленький (экран текста), безжалостно чистится: закрытое удаляется, не архивируется (архив — journal). Это дешёвый аналог «контекста коллеги, который отошёл от стола и вернулся».

## 8aa. Дисциплина журнала: три слоя, чтобы «забыл записать» не существовало

Проблема из дев-проекта: агент забывает журнал, ловится только на ревью. Решение — не полагаться на дисциплину модели вообще:

1. **Детерминированный action-log (не забывается по построению).** Каждый мутирующий вызов в `tools/ozon_api.py` сам пишет строку в SQLite: `когда, что, параметры, результат верификации, session_id`. Это ground truth аудита — модель не участвует. Журнал-markdown — это *нарратив* («почему»), а не единственный учёт.
2. **Stop-hook в моменте.** Claude Code hook на завершение сессии: скрипт грепает транскрипт сессии — были мутирующие вызовы (POST в ozon_api), а записи в journal/NOW нет → хук не даёт завершиться с напоминанием «запиши журнал и обнови NOW.md». Мягкое принуждение в моменте.
3. **Ночной секретарь (scribe).** Cron-агент в 02:00 проходит по транскриптам всех сессий за день (они лежат на диске в `~/.claude/projects/...jsonl`), сверяет с journal и action-log: пропущенные записи дописывает сам («по протоколу сессии №…»), протухшие пункты NOW.md флагает, невыполненные верификации — в алерт. Транскрипты — источник истины, поэтому секретарь ничего не выдумывает.

Слой 1 гарантирует учёт, слой 2 воспитывает, слой 3 подчищает. Идея «ежедневный агент дописывает по истории сессий» — это и есть слой 3, но с опорой на транскрипты и action-log, а не на память.

## 8b. Метрики самого агента (тюнинг дома)

Дев-агента меряет CI; нашего — еженедельный self-report в ретро:
- **скорость**: время от заказа/отзыва/алерта до реакции;
- **калибровка**: % апрувов T3, которые команда отклонила (высокий = плохо предлагаю), % ложных алертов (высокий = шумлю);
- **польза**: действия T1/T2 за неделю, деньги сэкономленные guardrails (вышли из минусовой акции и т.п.);
- **дисциплина**: расхождения drift-check, просроченные пункты NOW.md.
Плохая метрика → правка плейбука или guardrails, не «стараться лучше».

## 9. Верификация действий (аналог тестов Cursor)

Железное правило: **действие не считается выполненным, пока не подтверждено обратным чтением.**
- Изменил цену → перечитал `/v5/product/info/prices` → цена совпала → done, иначе retry/alert.
- Ответил на отзыв → перечитал отзыв → ответ виден.
- Вышел из акции → перечитал список акций SKU.
- Всё money-touching — сначала `dry_run=true` в тулзе (печатает что сделает), потом реальный вызов.

## 10. Субагенты (параллелизм Cursor)

Для тяжёлых задач — веер субагентов (как ресерч базы знаний 8 агентами):
- `researcher` — рынок/конкуренты/ниши, веером по источникам;
- `analyst` — копается в ledger/аналитике API, отвечает на «почему»;
- `copywriter` — тексты карточек, ответы на отзывы (черновики).
Главная сессия = диспетчер, субагенты не трогают деньги (только T0).

## 10a. Правила, заимствованные из внутреннего дев-проекта

Проверенные в бою на их проде; переносим с адаптацией под маркетплейс:

1. **«ЛК не редактируем руками» + drift-check.** Source of truth — наш репо/SQLite (цены, участие в акциях, тексты карточек). Ручная правка в ЛК Ozon мимо агента = дрейф. Ежедневный `drift_check.py`: фактическое состояние ЛК (цены/акции/карточки по API) == ожидаемое; расхождение → алерт в TG. Ручной хотфикс в ЛК — легален при пожаре, но в тот же день фиксируется в системе (как «хотфикс на проде → в git в тот же день»).
2. **Шаг 0 любой задачи: прочитай профильный док до первого действия.** Задача про цены → skill pricing + guardrails; про инцидент → RUNBOOK + похожие постмортемы. Не начинать с API-вызовов.
3. **Хвосты убираются в том же изменении.** Закрыл пункт BACKLOG — вычеркни; изменил поведение (гайдлайн, guardrail) — обнови стабильную доку; значимая задача — запись в journal; инцидент — постмортем. Стабильные доки — без дат и статусов; всё сиюминутное — только в journal.
4. **Постмортемы = память о том, как ломается именно наш магазин.** Каждый факап (просроченная отгрузка, требование ФНС, блокировка карточки, демпинг-война, ошибка ставки 42/43) → `docs/incidents/YYYY-MM-DD-<slug>.md`: симптом → root cause → как чинили → что поменяли, чтобы не повторилось → уроки. Агент читает их при похожих симптомах. Требования ФНС, блокировки карточек, просроченные отгрузки — первые кандидаты.
5. **PII не попадает в git/journal.** ФИО/телефоны/адреса покупателей с отправлений — никогда в репо; только синтетика или ID заказов.
6. **Freeze-окна.** В дев-командах это «не деплоить в пятницу». У нас: **не менять цены и не выходить из акций во время пиковых распродаж Ozon** без апрува (11.11, чёрная пятница) и в часы пиковых продаж — цена дёрнется у живой корзины.
7. **Узкие разрешения.** «Можешь поднять цену на Mini 4K один раз сейчас», а не «делай что нужно». Формулировка разрешения = его границы.
8. **HUMAN.md — гайд для команды.** Как ставить задачу агенту (цель+контекст+границы+критерий готовности, не решение), «сначала план, потом действия» для нетривиального, анти-паттерны оператора («сделай нормально» без критериев; пересказ по памяти вместо ссылки; знание в голове/чате вместо доки). Критично, чтобы операционщики получали от агента максимум.
9. **Периодический аудит → BACKLOG.** Раз в месяц агент сам проводит аудит системы (guardrails актуальны? роутины не отвалились? дрейф докок?) → пункты в BACKLOG с приоритетами.
10. **CLAUDE.md = AGENTS.md** (симлинк/дубль) — если рядом появится другой агент (Codex, свои скрипты), правила читаются из того же места.

## 10b. Дашборд — мини-проект внутри (и единственное место, где дев-паттерны возвращаются)

Панель управления на VPS: FastAPI + лёгкий фронт поверх `store.sqlite`:
- **витрины:** юнитка по SKU (live), P&L, история цен наши/конкуренты, лента action-log, журнал, статусы датчиков/роутин;
- **управление:** floor/ceiling per SKU (правка guardrails из UI), пауза роутины, ручной запуск задачи;
- **апрувы** дублируются из TG (TG — первичный канал, дашборд — обзорный).

Важно: это **дев-остров внутри ops-проекта** — единственная зона, где уместны классические паттерны (ветка, тесты, ревью), и его агент может строить сам по бэклогу в свободные циклы. Ops-режим (магазин) и dev-режим (апгрейд дома) явно разделены в CLAUDE.md: правила прод-осторожности дев-острова не ослабляют ops-guardrails.

## 11. Дорожная карта (порядок сборки)

**Фаза 1 — дом (1-2 дня), скрипты минимальны:**
1. `CLAUDE.md` конституция (+ цикл сессии из §8a) + `state/NOW.md` + `state/calendar.md` + 2-3 стартовых плейбука (new-order, morning-digest, reviews) + `HUMAN.md` + скелет docs/.
2. TG: развернуть **takopi** на сервере (готовый паттерн) → `@bot вопрос` работает сразу; cron-роутины дергают агент по расписанию.
3. Единственный скрипт фазы: тонкий `tools/ozon_api.py` (get-методы + dry-run) — остальное агент делает по плейбукам через skill.
→ **Дом обитаем: дайджест, алерты заказов с дедлайнами, вопросы в TG.**

**Фаза 2 — датчики + мост (неделя):**
5. `watchers/` (заказы, цены, отзывы, сток, drift) — чистый Python по крону, снапшоты в SQLite.
6. Свой tg-bridge (aiogram: `/send`, `/ask`, `/history`, кнопки) + скилл `tg` + очередь задач; action-log в `ozon_api.py` + stop-hook + ночной секретарь.
7. `pricing_engine.py` + ledger + Sheets-витрина; T2-коридор + апрув-механика T3.

**Фаза 3 — полнота:**
8. Отзывы/вопросы (T1 + драфты), акции-аудит, карточки, финучёт-роутина + налоговый чек.
9. Ретро-цикл, ресерч-роутины, новости платформы.
10. **Дашборд** (дев-остров, §10b) — агент строит сам по бэклогу.
11. WB — те же паттерны, второй набор тулз (skill уже есть).
